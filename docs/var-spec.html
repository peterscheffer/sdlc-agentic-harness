Vár Spec — Markdown as an Executable Specification

var-spec is an opt-in spec profile, an alternative to gherkin-bdd for the same kind of user-facing, behavioural scenarios. Instead of a separate .feature dialect, the spec is plain Markdown: a heading names the example, a sentence states a literal, checkable value, and a step definition binds that sentence to real application code. There are no Given/When/Then keywords to get right — the document itself is the test.

Not the default. gherkin-bdd remains the harness default. var-spec only activates when explicitly selected — via --profiles var-spec, sdlc.config.json's default_profiles, or by asking for it by name during the requirements Q&A. Don't select both gherkin-bdd and var-spec together — they cover the same scenarios.

Why it's different from Gherkin

Gherkin (gherkin-bdd)Vár (var-spec)
Separate .feature dialectPlain .md — renders on GitHub/docs sites as-is
Given/When/Then are load-bearing keywordsKeywords optional, purely narrative — a step is a stimulus or sensor by what it does, never by how the sentence starts
Assertion hand-written inside the step definition bodyAssertion is structural: the sensor's return value is compared against the literal value in the document
Failure points at the step definitionFailure points at the exact span in the Markdown where the claim broke

Triggering it

Select the profile at the requirements stage, either explicitly on the command line:

python3 .scripts/sdlc_harness.py --stage requirements --profiles var-spec --context "$CONTEXT_FILE"

or by setting it as a project default in sdlc.config.json:

{
  "default_model": "...",
  "default_profiles": ["var-spec", "unit-tests"]
}

or by asking for it during the requirements Q&A conversation (e.g. "use Vár / Markdown specs for this feature") — the LLM will recommend gherkin-bdd by default but honours an explicit ask for var-spec, and the confirmed choice is recorded in the requirements context footer:

SPEC_PROFILES: var-spec, unit-tests
SPEC_TOOLCHAIN: var-spec=pytest-var; unit-tests=pytest

What gets generated

The requirements stage writes one Markdown file per feature area to sdlc/requirements/var-examples/, plus a var.config.json at the project root that tells the Vár adapter which files are specs and which files bind their steps:

# User Login
A user with the correct password logs in successfully.
Given the user "alice" registered with password "secret123".
When alice logs in with password "secret123".
Then the login succeeds and returns a session token.

Notice the Given/When/Then words above are optional narration — Vár never matches on them. What must be checkable is the literal claim: "the login succeeds and returns a session token" is bound to a real step, not asserted by keyword.

Markup inside a matched sentence is significant. Vár matches the raw characters of a claim sentence — emphasis, links, and inline code are not stripped. Keep claim sentences plain; put styling only in the narration around them.

Step Definitions: Stimulus and Sensor

The coding stage generates step definitions as first-class targets alongside the application code. Every step is classified by what it does:

  • stimulus — arranges the starting state and/or acts on it (functional: receives state, returns the evolved state)
  • sensor — read-only; returns the value Vár compares against the literal in the document

Steps must stay thin (a couple of lines) and delegate to the real domain code — no mocks of the system under test. The logic lives in the application; the step definition is glue, and the assertion lives in the Markdown itself.

Toolchain by Language

The runner and step-definition location are chosen per project language (auto-detected, overridable via sdlc.config.json):

LanguageAdapterStep definitionsVerifier command
Pythonpytest-varsdlc/requirements/var-examples/steps/*.steps.pypython3 -m pytest
JS/TS@oselvar/var-clisdlc/requirements/var-examples/steps/*.steps.{js,ts}npx var run
Javavar-junitsrc/test/java/sdlc/varsteps/*Steps.java + RunVarSpecsTest.javamvn -q test / gradle test

JVM tooling is less mature. There is no var init CLI for Java/Kotlin yet, so var.config.json lists step classes by fully-qualified name (generated by the profile from each spec file's name) rather than a glob, and the JUnit suite class must exist alongside the step classes. Prefer gherkin-bdd on Java/Kotlin projects unless you specifically want var-spec.

Verification is Deterministic

Like every spec profile in this harness, var-spec verification is a real command's exit code — never LLM judgment. The coding stage runs the verifier inside its iteration loop, feeding failures back into the next iteration; the testing stage runs it again for the gate. If the language adapter isn't installed, the coding stage fails fast at preflight with the exact install command (e.g. pip install pytest-var, npm install --save-dev @oselvar/var @oselvar/var-cli) — there is no silent fallback.

The per-profile result is appended to TEST_REPORT.md, same as every other profile:

## Spec Verification: Vár Spec
**Status:** ✓ PASSED
**Command:** `python3 -m pytest`
**Exit Code:** 0
