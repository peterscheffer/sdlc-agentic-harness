Gherkin Specifications & Requirements Engineering

The requirements stage produces a structured REQUIREMENTS.md document plus one spec artifact per selected spec profile. When the gherkin-bdd profile is selected, that artifact is a set of executable Gherkin .feature files: the coding stage generates real step definitions for them, and the testing stage runs an actual BDD runner (behave, cucumber-js, or cucumber-jvm) — pass/fail is the runner's exit code.

Requirements Document

sdlc/requirements/REQUIREMENTS.md contains three structured tables (profile-neutral — it looks the same whether the solution is a UI, an API, a service, or a data layer):

SectionColumnsPurpose
Functional RequirementsID, Description, Priority (High/Medium/Low)What the system must do
Non-Functional RequirementsID, DescriptionPerformance, security, scalability constraints
Acceptance CriteriaID, Criterion, Verified ByVerifiable completion conditions, each mapped to the spec artifact that verifies it

Gherkin Feature Files

The LLM generates one .feature file per feature area, written in standard Gherkin syntax:

Feature: User Authentication

  Scenario: Successful login
    Given the user is on the login page
    When they enter valid credentials
    Then they are redirected to the dashboard

  Scenario: Failed login with invalid password
    Given the user is on the login page
    When they enter an invalid password
    Then an error message is displayed

Generated feature files are written to sdlc/requirements/ with kebab-case filenames (e.g., user-authentication.feature).

Executable Gherkin: Step Definitions + BDD Runner

Gherkin verification is fully deterministic. The coding stage generates step definitions as first-class targets alongside the application code; the testing stage executes the feature files with a real BDD runner and gates on its exit code. There is no LLM compliance judgment.

The runner and step-definition location are chosen per project language (auto-detected, overridable via sdlc.config.json):

LanguageRunnerStep definitionsVerifier command
Pythonbehavesdlc/requirements/steps/*_steps.pypython3 -m behave sdlc/requirements -f plain
Javacucumber-jvmsrc/test/java/sdlc/steps/*Steps.java + JUnit runner classmvn -q test / gradle test
JS/TS@cucumber/cucumbersdlc/requirements/steps/*.steps.{js,ts}npx cucumber-js sdlc/requirements --require <steps>

The verifier also runs inside the coding iteration loop: an unbound step or failing assertion feeds the runner output back into the next LLM iteration until the scenarios pass or the iteration budget is exhausted. If the runner is not installed, the coding stage fails fast at preflight with the exact install command — there is no silent fallback.

The per-profile result is appended to TEST_REPORT.md:

## Spec Verification: Gherkin BDD
**Status:** ✓ PASSED
**Command:** `python3 -m behave sdlc/requirements -f plain`
**Exit Code:** 0

Beyond Gherkin: Other Spec Profiles

Gherkin is one of several spec profiles; a feature can select any combination during the requirements Q&A (the LLM recommends based on the solution classification, the user confirms — or auto-accept adopts the recommendation):

  • unit-tests — requirements enumerated as concrete test cases in TEST_CASES.md, implemented and run with pytest / jest / vitest / JUnit. Best for services, business logic, integrations, and data layers.
  • openapi-contract — an OpenAPI document in sdlc/requirements/openapi.yaml, contract-tested against the running service with schemathesis. Best for REST APIs.
